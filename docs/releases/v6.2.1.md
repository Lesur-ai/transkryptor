# Release Notes — Transkryptor v6.2.1

Date de préparation : 2026-09-16
Branche cible : `main`

## Résumé

Transkryptor v6.2.1 est un hotfix de configuration, d'installation et de
sécurité :

- `qwen3.8:27b` remplace `qwen3.6:27b` comme modèle par défaut. Cloud Temple a
  déprécié `qwen3.6:27b` et le redirige vers `qwen3.8:27b` le 30 septembre 2026
  (changelog LLMaaS du 21/08/2026).
- L'installeur one-line installe de nouveau la version depuis laquelle il est
  téléchargé. Son `REF` par défaut était resté sur `v6.1.1` : les URLs
  d'installation `v6.1.2` et `v6.2.0` installaient en réalité `v6.1.1`.
- Les dépendances vulnérables sont mises à jour, dont `multer`, qui traite
  l'upload audio (dénis de service sur les requêtes multipart).

Le pipeline transcription / analyse / synthèse / diarisation est inchangé.

## Changements

- `.env.example` expose désormais cette allowlist :
  `qwen3.8:27b,mistral-small4:119b,qwen3.6:35b-a3b,gemma4:31b`, avec un lien
  vers le catalogue et cycle de vie Cloud Temple.
- `scripts/install.sh` clone `v6.2.1` par défaut.
- Nouveau contrôle `scripts/check-release-consistency.js`, sans dépendance npm.
  Il échoue si `VERSION`, `package.json`, `package-lock.json`, les fallbacks
  client/serveur, les URLs d'installation (README, release notes), le `REF` de
  l'installeur ou le changelog divergent. Exécuté contre les arbres des tags
  `v6.1.2` et `v6.2.0`, il signale bien le `REF` resté sur `v6.1.1`.
- `scripts/check-enable-thinking-fix.js` couvre `qwen3.8:27b`.
- Les versions projet, fallbacks client et fallback serveur sont alignés sur
  `6.2.1`.
- Les URLs d'installation README pointent vers le tag `v6.2.1`.

## Sécurité

Mise à jour limitée à `package-lock.json`, sans changement de version majeure
ni de plage dans `package.json` :

| Paquet | Avant | Après | Avis corrigés |
| --- | --- | --- | --- |
| `multer` | 2.2.0 | 2.4.0 | GHSA-wc9g-mqfw-jrwm, GHSA-qfvm-cv95-jqjf, GHSA-535w-7cp7-47q4 (high, déni de service multipart), GHSA-qvfw-j98x-7q72 (low) |
| `qs` | 6.15.3 | 6.16.0 | GHSA-x5fp-wj9c-mxmx, GHSA-4mjr-xmp4-gh2g (moderate) |
| `body-parser` | 1.20.5 | 1.20.8 | GHSA-v422-hmwv-36x6 (low) |
| `express` | 4.22.2 | 4.22.3 | via `qs` |

- `multer` gère `/api/transcribe`. Le serveur écoute sur toutes les
  interfaces : sans pare-feu, le déni de service est atteignable depuis le
  réseau local.
- `multer` 2.4.0 ne dépend plus de `concat-stream` (`buffer-from` et
  `typedarray` disparaissent aussi du lockfile). Version publiée par GitHub
  Actions avec attestation de provenance SLSA.
- `npm audit` ne signale plus aucune vulnérabilité connue.

## Compatibilité qwen3.8:27b

- Identifiant Cloud Temple : `qwen3.8:27b` (FP8), en production depuis le
  21/08/2026, contexte 250 000 tokens, fin de support annoncée au 30/12/2026.
- Qwen 3.8 fonctionne en mode thinking par défaut et conserve l'interrupteur
  `enable_thinking`. Le modèle correspond au motif `qwen*` : le backend lui
  envoie donc `enable_thinking: false`, comme aux autres Qwen, pour que la
  réponse arrive dans `message.content`.
- Aucun changement de code applicatif n'est nécessaire pour ce modèle.

## Impact utilisateur

- Les nouveaux déploiements créés depuis `.env.example` proposent
  `qwen3.8:27b` comme modèle sélectionné par défaut.
- Les correctifs de sécurité ne s'appliquent qu'après réinstallation des
  dépendances : l'installeur exécute `npm ci`, et Docker reconstruit l'image
  avec `--build`.
- Les fichiers `.env` existants ne sont pas modifiés automatiquement, y compris
  quand on relance l'installeur. Tant que `qwen3.6:27b` figure en tête de
  `CLOUD_TEMPLE_ALLOWED_MODELS`, il reste le modèle par défaut. Après le
  30/09/2026, selon la façon dont Cloud Temple publie la redirection, il pourra
  disparaître du menu (le modèle suivant devient alors le défaut) ou rester
  affiché sous son ancien nom tout en étant servi par `qwen3.8:27b`.
- Les installations faites avec la commande one-line `v6.1.2` ou `v6.2.0`
  tournent en réalité en `v6.1.1` : ancienne allowlist et échecs HTTP 400 avec
  les modèles Mistral. Leur `.env` contient des modèles absents du catalogue
  Cloud Temple actuel (`qwen3.5:397b`, `qwen3:235b`, `mistral-small3.2:24b`).

## Migration des installations existantes

L'allowlist n'est lue qu'au démarrage du serveur, et l'installeur ne redémarre
pas un service déjà lancé. Dans tous les cas, remplacer la ligne entière de
`.env` par celle de `.env.example` :

```dotenv
CLOUD_TEMPLE_ALLOWED_MODELS=qwen3.8:27b,mistral-small4:119b,qwen3.6:35b-a3b,gemma4:31b
```

Installation one-line (macOS) :

1. Arrêter le service :
   `kill "$(cat "$HOME/Library/Application Support/Transkryptor/transkryptor.pid")"`.
   Sous Linux, le fichier PID est
   `${XDG_STATE_HOME:-~/.local/state}/transkryptor/transkryptor.pid`.
2. Modifier `CLOUD_TEMPLE_ALLOWED_MODELS` dans le `.env` du dossier
   d'installation (`~/Applications/Transkryptor/.env` sur macOS).
3. Relancer la commande d'installation ci-dessous : elle met le code à jour et
   redémarre le service.
4. Vérifier : `curl -s http://localhost:3000/api/version` doit renvoyer
   `6.2.1`.

Docker : modifier `.env`, puis `docker compose up -d --build`.

Installation manuelle : `git fetch --tags && git checkout v6.2.1 && npm ci`,
modifier `.env`, puis redémarrer `npm start`.

## Validation recommandée

- `node scripts/check-release-consistency.js` (sans `npm ci`).
- `npm audit --audit-level=low` : aucune vulnérabilité.
- `bash -n scripts/install.sh`.
- Build Docker de l'image applicative, avec `multer@2.4.0`, `qs@6.16.0`,
  `body-parser@1.20.8` et `express@4.22.3` installés.
- Dans le conteneur Docker : `node --check src/server/server.js`,
  `node scripts/check-enable-thinking-fix.js` et
  `node scripts/check-release-consistency.js`.
- Smoke test HTTP Docker avec `--network none` et l'allowlist de
  `.env.example` :
  - `GET /api/version` attendu : `6.2.1` ;
  - `/api/analyze` refuse `qwen3.6:27b` (HTTP 400) et accepte `qwen3.8:27b`
    (l'échec ne vient que de l'appel réseau Cloud Temple) ;
  - `/api/transcribe` avec un upload multipart au format du client : `multer`
    lit le fichier et les champs, puis le fichier temporaire est supprimé.
- En environnement RUN avec clé Cloud Temple :
  - `GET /api/models` liste `qwen3.8:27b` en premier. Vérifier aussi que
    `qwen3.6:35b-a3b` est toujours proposé : le catalogue public ne liste plus
    que `qwen3.6:35b`, et la résolution dépend des alias publiés par
    `/v1/models`.
  - `/api/analyze`, `/api/synthesize` et `/api/diarize` avec `qwen3.8:27b`
    renvoient un contenu non vide dans `message.content`.
